# daily-dev-lab

設計から実装・検証・振り返りまでを、小さなアプリやDB課題で繰り返すための学習用リポジトリです。

> このファイルはリポジトリ直下の `README.md` として使用します。リポジトリ名は仮名です。`【記入】` などの記入欄を置き換えてください。各課題の詳細は、課題フォルダ内の `README.md` にまとめます。

## 1. 学習の目的と方針

**目的：小さな要求を自分で設計し、動作する形に実装し、検証結果と設計判断の理由を説明できるようになること。**

- 1日1アプリまたは1つのDB課題を目安に、実際に手を動かして学習する。
- 開発・実行・検証はローカルで行い、レンタルサーバーや外部公開を前提にしない。
- アプリ・DBともに、学習目標、要件、設計、完了条件を決めてから実装する。
- 同じ技術で数題取り組んだ後、別のフレームワークや設計方法で比較する。
- 1日で終わらない場合は「継続」と記録する。完成数を優先して設計や検証を省略しない。

| 項目 | 内容 |
|---|---|
| 学習開始日 | 【YYYY-MM-DD】 |
| 主な開発環境 | 【OS・WSLの利用有無・エディタなど】 |
| 現在の重点テーマ | 【例：入力検証とデータ保存】 |
| 現在使用する主な技術 | 【言語・フレームワーク・DB】 |
| 1日の学習時間の目安 | 【記入。必要に応じて調整する】 |

## 2. リポジトリの構成

```text
daily-dev-lab/
├── README.md                     # 全体の方針・課題一覧・進捗
├── templates/
│   └── PROJECT_README.md         # 課題用READMEの共通ひな形
├── projects/
│   └── 0001-example/             # 課題フォルダの例
│       ├── README.md             # その課題の要件・設計・手順・結果
│       └── ...                   # ソースコード・SQL・テストなど
└── .gitignore                    # 管理対象外ファイルの設定
```

これは配置例です。課題の内部構成は、使用するフレームワークや学習内容に合わせます。不要なフォルダは作成しません。

課題フォルダは `0001-web-memo`、`0002-inventory-db` のように、連番と内容が分かる名前を付けます。連番は課題IDであり、日付や連続学習日数ではありません。比較版・再実装版は別IDで作成し、元の課題を関連課題として記録します。

全体の学習順を別途整理する場合のみ、`ROADMAP.md` を追加します。既存の学習ガイドを保存する場合も、配置先に合わせてこのREADMEからリンクしてください。

## 3. 課題の始め方と進め方

1. 今日の主な学習目標を1つ決め、課題フォルダを作成する。
2. [課題用ひな形](templates/PROJECT_README.md)を、そのフォルダの `README.md` としてコピーする。
3. 課題READMEの「1. 学習目標」「2. 要件と対象範囲」「3. 設計」を記入し、実装前の状態をコミットする。
4. 最小の処理が入力から結果まで動くように実装し、必要な機能を追加する。「4. 実行・再作成・テスト手順」も更新する。
5. 実際に確認した内容を「5. 検証結果」に残し、「6. 振り返り」を記入する。課題READMEと、このファイルの課題一覧の状態を更新してコミットする。

設計を変更した場合は、変更理由を課題READMEに残します。実装途中で完了条件を見直す場合も、変更内容と理由を記録し、未確認の項目を確認済みにしません。

**共通の完了目安：** 課題ごとの完了条件を満たし、必要な正常系・異常系・境界値を検証し、READMEの手順で実行・再作成・確認できる状態にします。対象外の項目は理由を記録します。残課題は、完了を妨げる不具合と、将来の追加機能に分けて残します。

## 4. 課題一覧

> 下の行は記入欄です。実際の課題を追加するときに置き換えてください。未作成の課題を実施済みとして登録しません。

| ID | 課題名・READMEへのリンク | 種別 | 主な学習目標 | 使用技術 | 着手日 | 完了日 | 状態 |
|---|---|---|---|---|---|---|---|
| 【ID】 | 【課題名と相対リンク】 | 【アプリ／DB／準備】 | 【記入】 | 【記入】 | 【YYYY-MM-DD】 | — | 予定 |

リンクの書式例：`[メモ帳](projects/0001-web-memo/README.md)`。実際に作成したフォルダ名に合わせます。

状態は次のように使い分けます。

| 状態 | 意味 |
|---|---|
| 予定 | 取り組む予定があり、まだ着手していない |
| 進行中 | 設計・実装・検証などを進めている |
| 継続 | 当日の作業を終えたが未完了で、次回も続ける |
| 完了 | 完了条件を満たし、検証と記録を終えた |
| 保留 | 作業を止めており、課題READMEに理由と再開条件を記録している |

## 5. ファイルとGitの管理方針

課題ごとに依存関係を分離し、利用した言語・フレームワーク・DBのバージョン、依存関係の定義、利用する管理ツールのロックファイルを記録・保存します。複数課題をまとめて変更しないと動かない構成は、初期段階では作りません。

| Gitに残すもの | 原則として残さないもの |
|---|---|
| README、設計図、ソースコード、SQL、テスト、小さな検証データ、依存関係の定義・ロックファイル、秘密値を含まない設定例 | 仮想環境、`node_modules`、ビルド生成物、実行中のDBデータ、大容量ログ、パスワード・トークン・個人情報 |

DB課題は、作成SQL・初期データ・操作SQLなどから再作成できるようにします。初期化・削除の手順には、消えるデータの範囲を明記します。

コミットは、設計・実装・検証・記録の区切りで行います。次はメッセージの例です。

```text
docs(0001): 要件・設計・完了条件を定義
feat(0001): 最小機能を実装
test(0001): 正常系・異常系の検証を追加
docs(0001): 検証結果と振り返りを記録
```

完成した課題は、共通のメインブランチ上の各フォルダに残します。作業用ブランチを利用した場合は、作業終了後に統合します。

## 6. 学習の振り返り方針

複数の課題を終えた区切りで、以前の要件を別の技術・設計で実装するか、コードを見ずに再実装します。比較するときは、変更する条件と固定する条件を決め、分かった違いを課題READMEに記録します。

AIや記事の支援を受けた場合は、支援された範囲と自分で検証した内容を記録します。「動いたこと」と「自力で説明・再実装できること」を分けて確認します。

次の技術に進む際は、課題数だけでなく、処理の流れを説明できるか、小さな仕様変更に対応できるか、支援なしでどこまで作れるかを確認します。
